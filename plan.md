# Frontend and backend integration plan

## Baseline

This plan uses `frontend` (`a7728ed`) for the dashboard, `backend` (`cd651bb`) for FastAPI, and the local `origin/model` ref (`e9837fb`) for the V2 models and dataset. The attached Gemini brief describes the desired panel behavior. Its implementation directions are reference material for this planning task. The plan assumes the dashboard is a research simulator and that gauge inputs represent scenario values.

The frontend builds successfully. Vite reports a bundle-size warning, and Oxlint reports two existing React ref warnings in `InstrumentControls.tsx`. The backend's health and Model 2 routes passed the earlier HTTP smoke test on `backend`. The aggregate endpoint and merged V2 stack remain unverified at runtime.

## Current wiring and gaps

| Area | What exists | Integration gap |
| --- | --- | --- |
| App and API client | `src/main.tsx` mounts `App.tsx` in Strict Mode. `App` reevaluates on each material, dial, or gravity change. `src/services/avionicsService.ts` posts to `/api/avionics/evaluate`, optionally using `VITE_API_URL`, and falls back on errors. | FastAPI has no matching route. The default relative request reaches Vite, which has no `/api` proxy. The client trusts JSON shape, drops HTTP errors into synthetic output, and guards state updates without cancelling requests on input changes. |
| Backend model routes | `backend/app/main.py` mounts health, data, records, and model routers. `model2_routes.py` can rank materials, return a sustained-probability curve, and run the legacy probability-only solver. `model1_routes.py` and `model3_routes.py` return `501` and reuse Model 2 response schemas. | The standalone model contracts and the dashboard aggregate contract need separate schemas. Model 2 currently replaces a valid zero cutoff with the default. |
| V2 inference and data | `origin/model` contains `model1/`, `model2/`, `model3/`, `pipeline/inference.py`, artifacts under `models/`, V2 CSV/JSON, and `docs/BACKEND_ML_HANDOFF.md`. The Model 3 cascade consumes Model 1 spread. The aggregate pipeline evaluates all eight materials. | The active branches carry V1 artifacts. Move the V2 packages, artifacts, provenance and dataset together. The V1 ETL in `src/pipeline.py` writes the original CSV and `public/clean_combustion_data.json`. The current client does not fetch that JSON. |
| Controls and presets | `InstrumentControls.tsx`, `useAvionicsControl.ts`, `App.tsx` and `data.ts` own rotary controls, sample/target values, gravity and preset state. The spread display already renders but accepts edits and has fixed fallback values. | Keep the three input dials and make the spread meter an output. Reconcile duplicated control bounds and define whether chart scrubbing changes the simulation target. The current code couples chart scrubbing to airflow even though the README describes independent behavior. |
| Material ranking and drawer | `MaterialRisk.tsx` sorts visually by received row order, shows a static fallback, and opens a drawer. `App.tsx` interprets the selected index using the static catalog. | A backend reorder can select a different material in the chart and drawer. Live rows lack several fields the drawer expects, including presentation fields such as `location`. The table also blends Model 2 risk and Model 3 regime when assigning a badge. |
| Habitat status | `StatusPanel.tsx` has three fixed compartments and reads `sector_triage[index]`. The V2 pipeline returns eight probability-ranked material entries under that field. | Join materials to explicit sector IDs and define aggregation. A rank position has no compartment meaning. |
| Chart and evidence | `SimulationViews.tsx` draws a spread band, critical window and markers. `NasaEvidenceCard.tsx` handles provenance, drivers and the apply button. | Dataset and records | `data.py`, `data_rows.py` and `data_loader.py` expose CSV discovery, schema, pagination and stats. `records.py`, `data_service.py`, `models/orm.py` and `database.py` implement separate SQLite CRUD. | The data loader resolves `backend/data/processed`, while the tracked datasets live at `data/processed` in the repo root. The visual layout can be reused while the data source and state copy change. |

## Proposed implementation order

### 1. Assemble a coherent V2 checkout

- Start an integration branch from `frontend`. Bring in the `backend/` tree from `backend` and the model packages, `pipeline/`, `models/`, V2 dataset, model dependencies and handoff docs from `origin/model`. The model branch also contains older frontend files, so select the paths to bring over and review shared files such as `.gitignore` and `README.md` explicitly.
- Load the trusted V2 artifacts once per FastAPI worker through a shared model service. All three V2 pickles contain the scikit-learn `1.9.1` version marker, matching the backend pin. Keep the V1 CSV as an archive and verify startup with Python 3.11+ and the checked-in V2 artifacts. Check that all three models and provenance have the same canonical material keys and that their dataset version is exposed in the API.
- Centralize repo paths and runtime settings in backend configuration used by `main.py`, `database.py` and `data_loader.py`. Verify imports from the documented `backend` working directory and include model code and data in any packaged deployment. Keep `storage/records.db` and virtual environments out of Git.

### 2. Publish the dashboard contract in FastAPI

- Add `POST /api/avionics/evaluate` using the existing `TriModelPipeline.evaluate_avionics_state`. Use a synchronous handler or equivalent thread-pool boundary for inference. Validate canonical `material`, finite inputs, probability cutoffs including zero, nonnegative spread threshold, and bounded sweep counts. Return a useful `422` for invalid inputs and an observable unavailable state for model initialization failures. Use an explicit response model and generate frontend transport types from OpenAPI or check them against a shared fixture.
- Keep the existing dashboard request names and units (`oxygen_pct`, `pressure_kpa`, `flow_velocity_cm_s`, `cutoff_probability`, `spread_threshold_mm_s`, `sweep_points`). Echo accepted inputs and include model/data version and research provenance. Use a catalog endpoint such as `GET /api/avionics/materials` for canonical keys and V2 evidence, including materials before the first evaluation completes. Keep sector assignment and display aliases in the UI as scenario configuration.
- Preserve the Model 2 endpoints with their standalone contract. Replace the Model 1 and Model 3 stubs with model-specific diagnostic routes and corresponding schemas if those public endpoints are part of the release. Model 1 exposes spread and uncertainty; Model 3 exposes regime and global feature importances, using Model 1 spread for dashboard-consistent evaluation. The dashboard uses the aggregate route, so it does not need three browser calls per control adjustment. Keep the documented legacy aliases only where their semantics can be preserved.
- Fix dataset discovery against repo-relative V2 and archive files. Resolve dataset IDs from known files, return `404` consistently for unknown IDs, serialize missing values as `null`, and verify pagination and statistics. Keep SQLAlchemy records independent of dataset imports and model evaluation. Test the existing CRUD interface with a temporary SQLite database.
- Verify the V2 pipeline before exposing its payload. Model 1 and Model 2 each default their sweep to their own material bounds, while the current pipeline merges points by index. Use a shared X grid and test that the two models describe identical flow points. Keep the chart domain at 0–50 cm/s and distinguish extrapolated points from supported segments. Preserve Model 3's own range flag for triage, which the aggregate currently drops. Profile the local pipeline under realistic UI traffic and remove its duplicate solver evaluation by sharing the result between the chart and evidence.

### 3. Normalize the response at the frontend boundary

| Wire contract | Frontend change |
| --- | --- |
| `material_name` is the stable material key. Ranking rows carry predictions, LOI and flow windows, with fuller evidence in V2 provenance. | Select by key in `App.tsx` and `MaterialRisk.tsx`. Join catalog data, UI labels and live rows by key. Give the drawer a typed view model and retain selection when ranking order changes. Display `P(sustained)` because the classifier target is sustained versus extinguished combustion. |
| `spread_rate_meter` and sweep points carry spread, lower/upper bounds and `out_of_material_training_range`. Sweep points carry `probability_sustained` and omit the frontend's required `probability_extinguished` and `risk_status`. | Update `data.ts` transport types and derive UI-only fields in the adapter if used. Bind the meter to the response as read-only. Use the returned flow coordinates and spread bounds in the chart. Show out-of-range context for the operating point and applicable curve segments. |
| `airflow_simulation.material_name` and solver fields use V2 keys `probability_sustained` and `flame_spread_mm_s`. Candidate values can be `null` and an exact numeric zero is valid. | Adapt the shape once in `avionicsService.ts`. Use the exact matching input or nearest actual X for the operating point, with an explicit out-of-domain state. Draw a solver marker only for the displayed response's applicable candidate and use the returned spread at that candidate. |
| `sector_triage` is a material list. `hazard_regime` is `NOMINAL`, `ELEVATED` or `CRITICAL`. | Join by material key, group using configured habitat membership, and show the worst modeled regime and its contributing material per sector. Label the readings as scenario estimates. Confirm whether the subtitle should show that material's spread and sustained probability or a separately defined peak spread and LOI margin. |
| `hazard_drivers` are stored Random Forest feature importances shared across requests. `nasa_provenance` is material-specific and its `source_doi_url` may be an investigation URL. | Label the bars as global model feature importance. Use available evidence fields and call the link a source unless it is a DOI. Show missing provenance as unavailable. Keep Model 3 regime separate from Model 2 ranking risk. |
| Solver returns `dual_constraint_quench_found`, `probability_cutoff_only_quench_found`, `no_supported_quench_point_found`, or `conditions_outside_material_training_range`. | Keep the solver as a simulation preview. Enable a clearly labeled target-preview action only for a current, supported dual-constraint result. Update only the simulated airflow target. Hide the action for pending, stale, Earth, offline, partial and unsupported results. Remove the hardcoded `85 × airflow` RPM conversion and avoid presenting raw operational command text as an instruction. |

### 4. Connect browser state and modes

- Configure a Vite development proxy from `/api` to `http://127.0.0.1:8765`, with `VITE_API_URL` for an explicit server. Prefer same-origin routing in deployment and configure explicit allowed origins where a split deployment needs CORS. Document Windows setup, backend and frontend start commands, and the existing `/api/health/health` URL.
- Keep target dials responsive locally. Debounce model requests, abort superseded requests and clean up the timeout on every completion path. Key each response to the material, mode and input snapshot so late responses cannot update a different selection. Load each preset as one state update. Keep sample readings separate from target settings and label which one the current marker represents.
- Represent loading, loaded, stale, unavailable and Earth reference states explicitly. Show the last result only with its original inputs and a stale label, or show an empty state while waiting. Any retained demo mode should be explicitly selected and labeled. Remove fabricated defaults from live panels and retain the research-model qualification on inferred values.
- Use V2 catalog LOI for the Earth reference and implement the brief's `oxygen_pct <= loi_threshold_pct` comparison as a scenario rule. Show the threshold and outcome without fabricating probabilities, spread, confidence bands or solver results. Keep that mode local using the initialized catalog and display unavailable where LOI is missing. Treat a request for formal ground qualification as a separate requirement needing substantiated test criteria and records.
- Preserve the current panel layout, responsive grid, shared tokens, typography, drawer and gauge input behavior. Align visible attributions with the model and scenario shown. For evidence chat, retain the local corpus in the first dashboard integration. If backend retrieval is required, add it in a separate phase with an indexed corpus, a typed excerpt/citation endpoint, no-match handling and the existing `onSendQuery` entry point.

## Acceptance checks before release

1. From a clean integration checkout, install requirements, start Uvicorn with reload on `127.0.0.1:8765`, and start Vite. Check API readiness, catalog, V2 dataset routes, and browser Network responses over the proxy with no heuristic fallback.
2. Use a V2 fixture for all eight canonical material names. Compare API JSON with rendered spread, uncertainty, percentages, provenance and solver fields. Verify a 50-point sweep with a common X grid and test points outside a material's observed domain. Confirm stable selection across reranking and correct compartment grouping.
3. Cover unknown materials and dataset IDs, zero cutoff, invalid inputs, empty or missing data, model-load failure, delayed responses, timeouts and rapid dial changes. Exercise every solver status and verify that only the eligible simulation result can populate the target. Verify that no physical device command is emitted.
4. Exercise the three presets, Earth/microgravity changes, click-to-arm, wheel, drag, keyboard, responsive layouts and drawer. Verify that switching modes cancels pending ML work and that source links and evidence match the selected material. Check SQLite CRUD independently of dashboard evaluation.
5. Run `npm run build`, `npm run lint`, backend contract tests, and one browser smoke test against the live FastAPI process. Record the fixture, artifact version and results in the integration PR.
